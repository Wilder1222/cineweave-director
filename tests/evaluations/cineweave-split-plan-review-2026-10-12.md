## 2. 首次发现与必要修改

### F1 · 中优先级：P0 的哈希清单不能恢复含未提交成果的 A 组基线

首次位置：主计划第 42、198、202、271 行；首次 P0 只要求保存“本工作树源清单、输入集、上一构建”，而结尾直接进入 P1。

问题：计划正确指出较早 HEAD 不能代表当前精简后的单 Skill，但路径／字节／SHA 清单只能识别正文，不能重建正文。上一构建也只含分发文件，无法恢复当前未跟踪的 `scripts/contract-context.mjs`、`scripts/validate-prompt-projection.mjs`、`scripts/validate-shot-compiler.mjs`、新测试等开发内核。如果后续实施覆盖当前路径，仅依据清单和旧 HEAD 不能重跑 A 组或恢复 P1 前的准确工程状态。这是对照及回滚实际可执行性的缺口。

源码依据：

- `scripts/validate-repository.mjs:80–94` 的分发基础清单仅含入口、契约及随包辅助器；开发验证器不在分发层。
- `scripts/validate-repository.mjs:308–335` 从 lifecycle/index 生成分发清单；它没有把全部开发代码和测试带入包。
- `scripts/build-plugin-bundle.mjs:51–66` 校验后仅按分发清单复制文件，无法代替完整源码快照。
- `scripts/validate-output.mjs:11` 依赖开发侧 `contract-context.mjs`；当前上述文件在工作树中为未跟踪文件。

必要修改：P0 保存可重建、不可变、含准确正文的当前源快照，覆盖完整分发、所需开发代码／测试／清单和必要未跟踪源；输入及已知失败另行冻结。可以采用受控源码副本、存档或适用的 Git 快照，但不能只保存哈希，也不能默认用较早 HEAD。进入 P1 前，从快照独立重建／校验一次，并核对哈希。应保留原工作树和无关本地输出。

### F2 · 中优先级：P5 的默认采用门槛与“可选”性质矛盾

首次位置：主计划第 198、207、256 行。

问题：第 207 行最初把“收益及成本足以支持默认使用”作为进入下一阶段的证据，而第 256 行明确 C 没有足够收益时保持 B 默认。结合“阶段通过才扩下一项能力”，如果宿主无法委派，或 C 只是增加成本，那么已通过的 B 仍无法进入 P6。该阶段关系会迫使一个正确的负结果被视为发布失败。

必要修改：将 P5 设为 P4 后的可选评估分支。启用 C 需要准确交接、无污染／竞写及可接受收益成本；宿主不支持、C 未运行或 C 无收益时，记录相应状态，继续用已通过的 B 进入 P6。B 的兼容发布不能以启用 C 为前提；C 与 B 的结果仍分别记录。

这与主计划第 231–235 行的 A/B、B/C 对照安排一致，也与标准研究 E7–E10 对最简单有效流程、实际宿主支持和可选委派的范围一致。

## 4. 分组、所有权与闭包结论

## 5. 调用责任、兼容与评测结论

同代理按需读不同 Skill 是默认，只有独立研究和冻结稿件审阅才试委派；这是知识入口与执行控制分离。manager/handoff 被用作责任设计参照，没有声称项目已依赖 Agents SDK 或存在自动运行时。专业入口可直接交付限定结果，跨阶段请求由导演收口；评审返回问题与修复责任，不能自行批准上游。第 91–108、160–194 行对这些责任与缺失恢复给出了可执行边界。

准确正文、原请求、用户硬锁、决定、假设、未知、版本和哈希进入交接，有助于发现生产者输出未被消费者使用；缺元数据仍可草拟，正式绑定保留未知。计划没有把参考观察升级为权利，也没有假定宿主能够读取媒体或注册表。实际素材不可访问时限于文字和条件诊断，符合当前入口的非执行及证据约束。源码对应 `skills/cineweave-director/SKILL.md:37–42,59`、`references/core/operating-model.md:79–81`。

P1 先适配目录／打包，P2 单独提取平台，P3 参考，P4 评审，避免同时改变 Skill 数、Agent 数及创作规则。旧入口内联恢复路径和历史产物保留，版本与安装说明仅在相应阶段通过后改变；没有提前声称四 Skill 上线。各阶段验收可以映射到现有模块与反例，属于具体实施计划。

A/B 和 B/C 对照能区分拆 Skill 与委派的变量。24 条触发、八类内容、交接反例、工程反例及安装矩阵覆盖了主要风险；至少三次重复被明确限定为试点预算，没有作为普遍成功率。执行者不读取答案／判断规则，审阅者在输出完成后再判断，也避免先给评测者目标答案。完整首版、实际加载路径／哈希、工具状态、未决项、模型设置与工作量记录足以追踪失败。没有把字节数换算成实测 token。

实际图像／视频／音频单列待验，是正确的证据边界。新架构工程检查通过、旧版本 392 项回归、规范 schema/哈希通过，均未被当成身份、动作、时序、连续性或音画同步通过。单叶／全包静态检查与实际宿主发现也分开安排，没有假定插件目录存在即实际激活成功。

## 6. 后续阶段应显式定下的实施决策

以下不是本轮计划阻断缺陷；它们已归入未来 P1–P6 的交付范围，实施时应形成可检查的数据和命令。

1. **catalog 的主实现与恢复路径。** 单一 implementation owner 表示主责任，不应把导演保留的恢复行为误报为重复 owner。P1 应在 catalog／路由说明中区分当前启用主 owner、目标 owner 与恢复路径，并检查恢复只在专业入口缺失或不可用时启用、不会形成并行 canon。
2. **开发规范检查与安装后辅助检查的边界。** 首轮明确规范验证内核留开发／集成侧，而随包 helper 是有限只读检查。`scripts/validate-repository.mjs:80–94` 不分发 `validate-output.mjs`；安装后叶包的文档不得暗示已获得完整正式上下文验证器。隔离验收可由外部开发检查器验证叶包中的 schema／index及反例，但报告需记录实际验证器位置／版本；随包工具另在包外运行。若未来提供完整安装后规范验证，应再将相关 imports 和安全路径纳入派生映射。
3. **章节投影方式。** 42 参考中有平台／导演／评审混合说明；可以初期完整导出、按需章节读取，也可以生成投影，但必须保持本地 anchor、链接和来源可追溯。不能只按行截断或只按文件名确定语义权威。P1 要选定实际导出策略并用派生清单验证；方案选择前不宜宣称包已更小。
4. **实际宿主及版本矩阵。** 当前没有新入口安装或委派运行。P2–P6 应记录可知宿主、模型设置、准确目录／版本／哈希，并区分“静态包闭合”“实际被发现”“实际调用”“独立委派成功”。宿主缺该能力时用计划中的内联路径，不将其计入 C。

在上述实施产物形成前，无需增第 53 个根契约、修改 12 route 的业务身份、单独拆故事／资产，或引入供应商运行时。
