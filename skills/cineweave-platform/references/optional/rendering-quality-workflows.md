# 可选参考：渲染与画质方案

在用户要求画风落地、画质诊断、游戏引擎／三维方案、精确摄影机预演、抗闪烁、采样、跨软件色管或交付规格时加载。普通单图稿只取相关可见规则，无需编写整套引擎配置。

本指南维护创作选择、外部实施交接和验收方法，不增加引擎执行器、供应商调用、安装流程或生成回执。研究访问日期：2026-10-10。下面的路径选择和检查表是项目综合建议；链接说明对应工具机制，不能证明本项目已渲染、生成或验证画质。使用时核对实际软件／模型版本、界面、硬件、输出模式和来源日期，不把当前默认值写成永久预设。

## 风格与质量分开判断

风格按照[五维分解](../routes/style.md#风格分解与景别预算)描述造型、边缘、材质、色光和时间表现。质量先按目标表现体系判断，再检查技术输出。高质量插画不等于写实摄影，高分辨率文件也可能有错误的手、接触或材料。

| 检查层 | 具体证据 | 失败时优先返回 |
| --- | --- | --- |
| 内容与结构 | 身份、肢体、道具、文字、透视、尺度、遮挡与接触是否符合设计 | 人物／场景／动作设计，或生成输入 |
| 感知与细节可信度 | 主体是否清楚；材质响应和细节尺度是否可信；焦点、噪声、锐化、色阶是否服务目标 | 风格、摄影／用光、渲染或局部修复 |
| 时间一致性 | 轮廓、纹理、光照、身份、接触及运动是否按设计延续；相邻镜头是否匹配 | 动画／缓存、采样／历史、生成模式或连续性 |
| 编码与交付 | 实际分辨率、帧率、位深、像素格式、色彩标签（原色／传递函数／矩阵／范围）、压缩、音画同步和完整性是否符合用途 | 输出／转码／装配计划 |

上采样和加锐不能替代结构修复，去噪不能证明细节真实。胶片颗粒、光晕和运动模糊是有条件的表现手法，不用来遮住失败。文件检测只证明规格；还需要实际画面与播放证据才能声明视觉通过。

## 根据约束选择制作路径

先判断是否需要精确空间／摄影机、能否接受资产制作成本、是否已有可复用项目、最终画面由谁产生，再选择路径。以下是工程与创作取舍，不是工具排行榜。

| 路径 | 更适合的条件 | 本 Skill 的交接内容 | 必须保留的未知项 |
| --- | --- | --- | --- |
| 纯 AIGC | 短镜头、探索性美术；空间和接触可通过素材与试片评审收敛 | 视觉基线、参考职责、完整可见提示词、采用窗口和关键验收点 | 模型对数值摄影机、细动作、身份和时序的实际控制程度 |
| UE 预演 → AIGC | 需要先验证通路、遮挡、轴线、动作相位；最终想用 AIGC 外观 | 白模／相机计划、关键帧或预演片段的参考职责、允许重绘与必须保持项 | 目标生成入口是否支持该类参考；不能假定会逐帧忠实重建 |
| UE 最终渲染 | 已有 UE 资产、复杂环境与多镜复用；需要可控摄影机和可重复场景 | Sequence 与镜号映射、演员／相机轨、灯光材质意图、渲染路径、采样及色管试验计划 | 资产、材质、特效、硬件与所选渲染路径的实际兼容性 |
| Blender 预演／最终渲染 | 定制几何、绑定、风格化材质、离线合成；已有 Blender 制作资源 | 相机／单位交接、动画与模拟缓存、材质表现规则、Cycles／EEVEE 取舍及输出计划 | 引擎特有节点、轮廓／透明、去噪与合成在实际版本中的表现 |
| 已有 Unity 项目 | 团队已有 Unity 资产、Timeline／摄影机流程和兼容渲染管线 | 沿用项目的渲染管线、版本与资产约束，输出同样的镜头和质量交接 | HDRP 包与 Editor 的组合、硬件、数字人／材质样例的版本适配 |

引擎负责确定的几何、摄影机、动画、灯光与渲染；AIGC 负责按实际入口支持的语义／参考生成。不要把 UE 白模导入视为真人演技、把 Blender 路径当成自动视频生成服务，或为了“电影感”重建已有合格资产。

Unity 官方将 HDRP 用于需要较高图形质量的高端平台，并要求兼容硬件；它是可选实现条件，不能据名字承诺最终质量。[Unity 6 HDRP 文档](https://docs.unity.com/en-us/engine/6000.0/manual/render-pipelines/high-definition-render-pipeline)（访问：2026-10-10）。

## 最少而完整的外部交接

当前镜头使用以下自然语言工作表即可。结构化需求映射到既有 `CameraPrevisSpec`、`RenderPlan`、`ColorPipelineProfile` 等契约，不另建同名执行协议。

| 交接项 | 必需内容 |
| --- | --- |
| 目的与不变量 | 镜号、可见事件、人物／服装／空间、画幅、共同风格；需要保持与允许改变项 |
| 版本与材料 | 实际软件／模型、界面／插件／渲染管线版本，引用材料及其职责，未知能力 |
| 摄影机与时间 | 传感器／裁切、位置与姿态、焦距、对焦、光圈、快门约定；有理数帧率、采用边界、子帧及余量 |
| 动画与效果 | 演员、道具和摄影机各自的轨；接触时刻、缓存与预热范围、程序化随机状态 |
| 风格与光色 | 五维表现规则、物理光源与曝光意图、材质差异、创意调色和技术色管 |
| 输出与检查 | 原始／合成／交付的规格假设，代表性试片、需检查缺陷、保留通过项与失败回流 |
| 实施归属 | 外部操作者或工具负责的下一步，以及哪些画面和元数据需要返回；没有实际文件不填写结果位置或成功状态 |

摄影机跨软件交换按[摄影机预演](camera-previsualization.md)完成单位、坐标、视场与时间验证。对 AIGC 入口只提交实际支持的参考；深度、法线、姿态、相机轨不能因为引擎可以导出，就被假定为目标模型可读的控制槽。

### 交接示例：同一可见目标，两种实施路径

以下是假设镜头，用来说明编译方式，不是已批准故事或测试结果：人物从阴影中走到窗边，摄影机横移保持中景；衣料从低反差阴影进入柔和侧光，窗框短暂遮挡人物后脸部重新可见；反光金属扣与亚光布料仍有清楚差异。

- **给外部 UE／Blender 操作者。** 先依据已声明的走廊尺寸和站位建立白模，分开人物与相机轨，检查窗框遮挡的进入／解除时刻及地面接触；沿共同曝光意图设置源光和相机，不让自动曝光将阴影强行提亮。用同一短片段比较布纹、金属高光和遮挡后的人脸，记录渲染路径、采样、去噪及观察变换。尺寸、软件版本和具体参数未提供时列为待确认实施项，不填虚构数值。
- **给 AIGC 入口的可见稿。** “摄影机平稳向右横移，保持人物中景及原有面部与衣着。人物连续走到窗边，经过窗框的短暂遮挡后重新露出同一张脸，步态与朝向连续。柔和窗光逐渐照到肩部和侧脸，衣料保留亚光褶皱，金属扣产生窄而明亮的高光，背景阴影保持原有深浅关系；光照随人物靠近窗边变化，画面整体亮度保持稳定。”按实际首帧／参考继承事实，另附采用时长和验收点，不声称数值相机轨或固定曝光已被模型执行。

两条路径检查同一身份、遮挡、接触和材质目标；引擎路径另需看几何／渲染设置，AIGC 路径另需看参考遵循和时间漂移。没有返回片段时，两者均只是待检方案。

## UE：先区分视口、渲染路径与输出配置

Epic 的 Movie Render Pipeline 面向离线图像序列和线性内容；MRQ 用于队列与配置，MRG 用图组织渲染操作。它们管理输出，不自动修复资产、动画或镜头意图。外部计划注明实际使用哪一种，不直接将 MRQ 设置名复制到 MRG 节点。[官方流程](https://dev.epicgames.com/documentation/unreal-engine/movie-render-pipeline-in-unreal-engine)（访问：2026-10-10）。

- **Lumen 的选择。** 适合先判断动态照明与大场景互动，最终输出仍要检查视角变化和时间稳定性。官方说明其先作屏幕追踪、再用其他追踪方式；快速相机移动可能导致场景更新落后。项目建议先对比问题部位的 Lumen Scene／Surface Cache 与实际几何，检查薄墙、小发光体、反射和快速转向，再决定是否调整覆盖、几何或渲染路径。不要一出现闪烁就堆时间采样。[Lumen 技术说明](https://dev.epicgames.com/documentation/en-us/unreal-engine/lumen-technical-details-in-unreal-engine)（访问：2026-10-10）。
- **Path Tracer 的选择。** 适合需要离线光照参照或更完整路径追踪的镜头，但先核查角色毛发、材质、体积与运动支持，再估算样本和时间。MRQ 的空间样本与时间样本作用不同，Reference Motion Blur 等选项还会改变累积与去噪关系；不能把另一个模式的数字当通用配置。[Path Tracer 官方说明](https://dev.epicgames.com/documentation/en-us/unreal-engine/path-tracer-in-unreal-engine)（访问：2026-10-10）。
- **相机与曝光。** 预览沿用最终传感器／裁切、焦距、对焦与曝光关系。常量曝光或有意的曝光轨要在交接中明确，不能让自动曝光无记录地改变镜头间反差。人物转入暗处可以有动机变化，具体受光仍遵守场景光源与共同视觉基线。
- **采样与预热。** 分开记录空间采样、时间采样、抗锯齿方式、模拟预热与渲染历史建立。只推进场景不等于已建立 GPU 历史。子帧采样访问的角色／相机轨与缓存需覆盖快门和剪辑余量；从切镜开始而无前置状态的模拟需专门试片。[MRQ 图像设置](https://dev.epicgames.com/documentation/unreal-engine/cinematic-rendering-image-quality-settings-in-unreal-engine?lang=en-US)（访问：2026-10-10）。

先让外部实施测试一个静止细节区和一个包含真实运动、遮挡与切点的短片段，每次只调整影响当前缺陷的参数；返回正常播放与局部帧观察，再扩大输出。本项目不采用官方演示中的固定高采样／预热数字。Epic 也建议先测试少量帧，按项目和硬件找到合适设置。[高质量渲染指南](https://dev.epicgames.com/documentation/unreal-engine/rendering-high-quality-frames-with-movie-render-queue-in-unreal-engine)（访问：2026-10-10）。

## Blender：表现规则决定引擎与去噪试验

先用低成本预演确定构图、遮挡、接触和时间，再比较目标表现需要的实际着色能力。Cycles／EEVEE 不只是快慢档位，切换前必须检查材质、透明、反射、阴影、轮廓与合成节点是否兼容；写实作品不自动选最高样本，风格化作品不自动要求路径追踪。

Cycles 的自适应采样根据噪声阈值决定哪些像素继续采样；去噪可以使用颜色、Albedo 和 Normal 输入。外部计划保留有／无去噪的细节对比，并检查眼睑、发丝、布纹及运动中的细线，避免把平滑误判为质量提升；单帧干净还需用片段检查时间稳定性。[Blender 4.4 采样说明](https://docs.blender.org/manual/en/4.4/render/cycles/render_settings/sampling.html)（访问：2026-10-10；该页版本不代表当前工程版本）。

Blender 4.5 LTS 文档区分 AgX、Standard、Khronos PBR Neutral 等观察变换，并要求法线／位移等数据贴图按 Non-Color 解释。AgX 是特定观察／色调映射选择，不能仅因它被启用就宣称工程使用 ACES。按作品需要选择观察变换，并用相同变换比较候选；更换变换后重新检查高光、肤色与材料色。[Blender 4.5 LTS 色管说明](https://docs.blender.org/manual/sr/4.5/render/color_management.html)（访问：2026-10-10；引用页主体提供相关英文说明）。

## 色管：创意调色与技术变换各自有来源

交接最少说明输入素材的编码／色彩解释、工作空间、曝光与创意处理、观察变换、目标显示／输出编码及哪些处理已经烘焙。未知 AIGC 输出不能被重新标为相机 Log、RAW 或 scene-linear；无法证明输入空间时注明假设，先做一致显示下的有限比较。

ACES 的 Output Transform 将场景参照数据变成面向指定显示与观看条件的输出；因此“用了 ACES”必须能指出实际配置版本与变换链，不能用一张 LUT 或近似 filmic 外观代替。是否采用 ACES 由项目交换需求决定，AgX 或明确管理的其他流程也可以服务当前作品。[ACES Output Transforms](https://docs.acescentral.com/system-components/output-transforms/)（访问：2026-10-10）。

UE 的 Color Output 可使用 OCIO，也能控制 Tone Curve；EXR 输出是否保留所需线性数据还取决于实际设置。文件扩展名不能单独证明 scene-linear、ACES 或显示状态。交接检查 UE 输出、合成输入和最终显示是否重复应用观察／色调变换。[UE 渲染设置与格式](https://dev.epicgames.com/documentation/en-us/unreal-engine/cinematic-render-settings-and-formats-in-unreal-engine)（访问：2026-10-10）。

外部操作者用相同参考图与一段高光／深阴影并存的测试素材对齐软件间观察条件，再核对最终转码。皮肤、饱和材料、发光物和黑位分别检查，不能仅靠画面“更艳”判断正确。SDR 与 HDR 交付分别记录目标和证据，不把 HDR 标签或高位深当作创意质量结论。

## 抗闪烁与画质诊断

以下是项目诊断顺序。先定位真实素材中的空间位置、发生时刻和触发变化，再选对应原因；没有素材时只能列候选原因与试验计划。

| 可见缺陷 | 先区分的原因 | 有界修复与复查 |
| --- | --- | --- |
| 人脸、手或道具形态逐帧改变 | AIGC 身份／结构漂移，或动画／绑定故障 | 修输入锚点、动作难度或绑定；核对转身与遮挡后的身份，不能用加锐修 |
| 布纹、发丝、轮廓闪动 | 纹理细节超过当前像素预算、LOD、阴影／采样或逐帧生成纹理 | 比较原始帧与最终编码；只调细节尺度、对应抗锯齿／采样或参考策略，保留通过部分 |
| 动作后留下旧轮廓 | 时间历史、去噪／重建或运动模糊不匹配；也可能是有意涂抹帧 | 对比相同动作的处理开关；恢复轮廓和接触可读性，先遵守已批准时间语法 |
| 机位转动后反射／亮度跳变 | 屏幕相关效果、场景覆盖、曝光轨、真实遮挡或生成照明漂移 | 检查变化动机与问题区域；在引擎内对比对应可视化，AIGC 则修光源／相机约束 |
| 首帧异常、衣发／粒子突然稳定 | 模拟缓存、预热或历史不足，或采用区间含不适合的边界 | 补真实可求值范围并检查切入；调整采用窗口前确认完整动作与对白仍保留 |
| 皮肤蜡化、眼睛僵硬 | 材质响应、去噪、过度磨皮，或眼神／眼睑／表演时间错误 | 分开修材质和表演；在目标近景与运动中检查，不把数字人模型质量当演员表现 |
| 暗部块状、渐变断层或细节糊掉 | 源图本身、显示解释、压缩／缩放或过度处理 | 在相同观看条件下比对源与交付版；修对应环节而非改人物设计 |
| 镜头之间颜色不一致 | 源照明变化、创意调色变化、输入空间解释或重复变换 | 核对共同光色意图和变换链；相邻镜头播放检查，不靠套统一滤镜掩盖 |

有意的二维保持画格、线条沸腾或涂抹帧只有在风格规则中明确并服务动作时才可接受；随机身份变化、接触脱落和无因果照明跳变不能靠“风格化”免责。

## 可复现经验的采用与排除

- **采用作者解释，排除万能数字。** Shaun Comly 的 [Demystifying Movie Render Queue](https://dev.epicgames.com/community/learning/tutorials/GxdV/unreal-engine-demystifying-movie-render-queue)解释 MRQ 的预热、时间采样和求值过程（访问：2026-10-10；教程最初发布于 2022 年，页面列出更新及适用版本）。采用“先理解当前渲染路径与时序，再针对缺陷试验”的做法；具体样本数、控制台变量、奇偶采样建议需按当前版本和动作检查，不直接变成默认配置。
- **采用分系统检查，排除成片背书。** Unity Demo Team 的 [digital-human 固定源码](https://github.com/Unity-Technologies/com.unity.demoteam.digital-human/blob/8d61864050277f2c4574df7b31beb70093a8c263/README.md)及其[样例说明](https://github.com/Unity-Technologies/com.unity.demoteam.digital-human.sample/blob/15e3fe2c88fe5c5064ad753ee9d121060eab867a/README.md)把面部动画、皮肤附着及眼睛／皮肤／牙齿／毛发着色列为不同系统（访问：2026-10-10）。本项目据此分别检查变形、附着、材料和表演；历史最低版本要求不证明新工程兼容，作品展示不证明当前角色质量。没有检查实际素材、依赖与许可，不宣称已导入或可直接商用。
